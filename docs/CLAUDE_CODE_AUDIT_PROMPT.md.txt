# Claude Code: Codebase Overhaul & Audit Prompt


## Context


This is a Next.js design portfolio for a Social Impact Designer (lorin.work). It was built iteratively through vibe-coding across many Claude conversations. The code works but has accumulated inconsistencies, dead code, stale comments, and disorganized file structure. The goal is to make this codebase look like it was built by someone who respects engineers — clean, consistent, well-documented, and easy to collaborate on.


**This is NOT a redesign.** The visual design and content are intentional. This is a structural, organizational, and code-quality overhaul.

5. **Git safety.** Before beginning destructive work, confirm I have committed and pushed current state. Create a new branch called `codebase-overhaul` for all changes.

### What Might Not Belong

```
│   │   └── Nav.module.css
│   ├── Footer/
│   │   ├── Footer.js
│   │   └── Footer.module.css
│   ├── [ComponentName]/
│   │   ├── [ComponentName].js
│   │   └── [ComponentName].module.css
│   └── index.js          ← barrel file for clean imports
├── content/
│   └── projects/
│       ├── groundswell.md
│       └── [other-project].md
├── lib/
│   └── [any utility functions, data helpers, constants]
└── styles/
    └── [any shared style tokens or mixins if needed]


public/
├── images/
│   ├── projects/
│   │   ├── groundswell/
│   │   └── [other-project]/
│   ├── site/              ← logo, favicon, general site images
│   └── [organized by purpose]
├── audio/
├── video/
└── fonts/                 ← if any local fonts
```


**Rules:**
- Every component gets its own folder with its `.js` and `.module.css` file
- No loose component files at root level
- All imports must be updated to match new paths
- Create a barrel `index.js` in `components/` for clean imports: `import { Nav, Footer } from '@/components'`
- Group assets by project/purpose, not by file type
- Run build after reorganization to confirm nothing broke

## Phase 3: Code Cleanup


### Comments
- **Remove:** Any comment that just restates what the code does (`// set state to true`)
- **Remove:** Any AI-generated meta-comments (`// Added this section`, `// Per user request`, `// This component handles...`)
- **Remove:** Any commented-out code blocks (if they seem important, flag them for me first)
- **Keep/Add:** Comments that explain WHY a non-obvious decision was made
- **Keep/Add:** Brief JSDoc-style comments at the top of each component explaining its purpose and props
- **Format:** Comments should be concise, lowercase-start for inline, sentence case for block comments


Example of a good component header comment:
```js
/**
 * ProjectCard — Clickable card linking to a case study.
 * Displays project thumbnail, title, tags, and brief description.
 * Used in: Homepage featured work section, project gallery pages.
 *
 * @param {string} title - Project display name
 * @param {string} slug - URL path segment for routing
 * @param {string} thumbnail - Path to preview image
 * @param {string[]} tags - Category labels shown on card
 */
```


### CSS
- Consolidate CSS custom properties into `globals.css` under a clear `:root` section with organized groupings (colors, typography, spacing, motion, breakpoints)
- Ensure every component uses CSS Modules — no rogue global class names
- Remove duplicate or overridden styles
- Use consistent naming: `camelCase` for CSS Module classes
- Add responsive breakpoints as custom properties or clearly documented values
- Check for any `!important` usage and eliminate where possible


### JavaScript
- Consistent use of arrow functions vs function declarations (pick one pattern per context)
- Remove unused imports
- Remove unused state variables or effects
- Ensure proper dependency arrays in `useEffect`
- Ensure images have proper `alt` text (descriptive for content images, empty string for decorative)
- Ensure semantic HTML (`<main>`, `<section>`, `<article>`, `<nav>`, `<header>`, `<footer>`)


### Accessibility Quick Pass
- All interactive elements are keyboard accessible
- Focus states are visible
- Color contrast meets WCAG AA minimum
- Skip-to-content link exists
- Heading hierarchy is logical (no skipped levels)
- Images have alt text
- ARIA labels on icon-only buttons
